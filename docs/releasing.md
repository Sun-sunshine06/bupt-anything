# 本地验证与发布流程

本文件不授权任何推送、远端创建或可见性修改。公开发布由维护者另行决定。

## 候选版本

1. 整理并检查当前工作树，而不是直接导出可能落后的旧 HEAD。
2. 使用明确的文件清单复制源码、合成测试、公共文档和配置到新目录。不得复制旧 `.git`、`private/`、`artifacts/`、缓存、凭据、下载文件或旧构建包。
3. 在新目录创建独立 Git 仓库，仅提交一次初始版本，不配置 remote。
4. 使用 `uv sync --frozen` 安装，从该新目录运行 `bash scripts/check.sh`、`uv build`。安装包不代表已上传到包索引。
5. 检查 Git 仅有一条提交、没有父提交、没有远端、工作树干净；检查包成员和文本，不含个人内容与移除的功能。

## 公开前人工核对

- 阅读 `docs/sources.md`，核对协议参考与代码来源，处理未明确授权的代码借用；当前来源记录仍列出需核对项，不能把本地候选版本等同于完成法律审查。
- 确认仓库描述、许可证、版本、安装说明、支持平台与功能范围一致。
- 为发布仓库启用并验证 GitHub 私密漏洞报告入口。未配置前 SECURITY.md 的报告流程不是已上线服务。
- 如要发布到 PyPI，先确认包名可用和发布账号，不在仓库中保存上传令牌。本项目未声称已在 PyPI 发布。
- 本地重新构建并核验测试；CI 配置存在不等于远端 CI 已运行通过。

## 归档与维护

源码归档应从干净发布仓库的初始提交生成，不打包 `.git` 或整个开发目录。记录初始提交 ID、归档哈希和验证结果，用于比对。

旧私有开发仓库可保留作内部记录。不要向发布仓库合并旧分支、推送镜像或重新引入旧历史。后续修改应以干净发布仓库为基础。
